# DATA-01：独立规则资料库设计

日期：2026-10-31。状态：设计稿，待用户评审；不是已实现能力。

## 1. 目标与已确认决策

为家用电器售后工单提供集中维护、按范围与时间选择、可追溯的处理规则。客服能看出建议使用的资料及版本，开发者可以更新规则而不逐份修改工单。

用户已确认：日常分析使用独立规则库；历史回放和固定评估使用工单规则快照；缺资料时如实说明，两种模式不自动混用。界面美化继续暂缓。

其余具体设计为本稿的推荐方案。第一版成功标准：正确选取适用规则、明确无匹配或冲突、留存实际引用、保留现有只读资金权限及固定评估的可重复性。

## 2. 方案选择与范围

| 方案 | 收益与代价 | 决定 |
|---|---|---|
| 每次直接读取JSON | 改动少，但运行期间文件变化、版本选择与引用留存需另处理 | 不作为本版运行方式 |
| PDF原件、登记信息、按页解析后导入SQLite | 保留原始依据，支持范围查询、页码引用、版本与运行快照 | 推荐，按用户资料形式修订 |
| 语义检索/向量库 | 需由实际资料规模和召回评估证明收益 | 后续再评估 |

本版推荐支持可提取文字的PDF、开发者本机登记、解析核对和发布、只读检索、页码引用及测试评估。沿用Python、FastAPI、单Agent、SQLite。不增加规则编辑后台、网页美化、自动爬取、OCR、向量库、品牌政策推断或自动退款。

初始资料由项目构造，标为项目处理参考。只有实际取得并核实的资料才能标注对应来源；不填造质保期限、退款资格、赔付金额或品牌服务承诺。

## 3. 规则数据契约

规则正文来自PDF，不手工重写成JSON条款。数据分三层：原始PDF；描述来源、版本和适用范围的JSON登记信息；按页提取、可重建的文字与检索片段。公开资料建议分别存放于 `data/policies/documents/` 和 `data/policies/manifests/`；私有原件放在Git忽略目录。它们不是工单，不含客户数据或评估答案。

资料类别包括售后处理流程、退换货处理说明、型号保修卡、安装使用说明书和配送服务说明。项目自编资料须标为项目处理参考，不能冒充品牌政策；实际条款取自取得的文档，不虚构期限和金额。

| 字段 | 含义及限制 |
|---|---|
| schema_version | 文件契约版本，初始为1 |
| policy_id / version | 稳定规则系列编号、正整数版本；同店铺下编号和版本唯一 |
| shop_id | 精确店铺编号，无跨店铺全局通配 |
| title / topic | 标题及主题，例如配送核查、退款人工处理、商品异常补证 |
| scope_type / scope_value | shop、category、product；品类/商品范围必须有明确值 |
| source_kind / source_name / source_ref | 项目参考或已核实资料的来源类型、名称和受控引用；名称不是权威证明 |
| effective_from / effective_to | 带时区的业务生效区间，左闭右开；结束可为空 |
| file_ref / sha256 | 受控PDF引用及文件哈希；模型不能指定任意文件路径 |
| extraction_revision | 解析器、分段版本及提取修订 |
| chunks | 从PDF提取的片段：chunk_id、原文、物理页码起止；不是人工编造的条款 |

物理页码从1开始，可另存印刷页码标签，不能混用。片段需尽量保留条件、例外、金额单位及表头上下文。原文未载明的有效期不能由模型补造；未知时间资料只可作为待核对参考，不冒充已核实现行规则。扫描页、空白页与解析失败须区分，混合PDF不能只解析部分页面就宣称完整。

商品范围按当前案例已校验的商品编号精确匹配；品类按目录中的category原值精确匹配，不使用模型猜测或语义相似度。信息不足时只考虑店铺通用规则。实际型号专属资料必须使用稳定商品/型号编号，不以宽泛商品名称替代。

第一版只承载以案例处理时间为依据的处理指引，时间基准固定为 `metadata.snapshot_at`。不处理需要按购买日、合同订立日等不同时间基准裁决的资格或权益条款；此类资料在具备明确契约前不发布为自动适用规则。

## 4. 维护、校验和发布

推荐维护流程：登记PDF与范围 → 校验受控文件、大小及类型 → 按页提取 → 检查缺页、乱码及表格错位 → 维护者核对关键原文和页码 → 发布 → 运行检索用例。JSON只登记资料，解析结果由程序生成。开发者维护，不提供Agent写入工具或公开写接口。扫描件或提取不完整标为待处理，不以模型摘要代替原文发布；解析修订不能覆盖旧运行引用。

校验包括字段类型、编号、范围、主题、带时区时间、有效期顺序、条款编号唯一、来源必要字段及文件大小。正文只作为不可信业务资料；结构合格不证明语义正确或来源权威，发布前由维护者审阅。

导入使用事务：任一文件失败则该批次全部不发布。相同店铺/编号/版本且内容相同视为重复导入，不新增；相同编号和版本但正文、来源或范围不同则拒绝，要求增加版本。

已发布正文、来源和适用范围不可原地覆盖。新版本需明确其替代的旧版本，版本号递增、生效时间向前推进；同系列范围和主题保持稳定。发布事务可将旧版本有效期收口到新版本生效时刻，并保存前后值的审计记录；旧版若已声明更早失效，则不延长该失效时间。旧结果保留当时冻结的有效期与正文，不回写。

同店铺、同文档系列不允许有效版本含糊重叠；不同系列的互补资料可以同时发布，即使主题相同也不直接认定冲突。明确的新版本替代可在同一事务中收口旧版本。已登记矛盾或异常版本重叠时报告冲突，不按第一条或最大版本号随意选择。自然语言矛盾仍需维护者审阅。

## 5. 查询和适用性

适用文档筛选由程序完成，再在候选文档中检索与诉求相关的原文。Agent沿用受限的get_policy能力，不能自行指定其他店铺、时间基准、读取模式或文件路径。检索查询契约在实施计划中确定。

先采用SQLite文字索引与关键词检索；中文需验证分词或字符切分以及同义表达召回，不能默认英文分词器适用。无相关片段与没有适用文档分别报告，搜不到不等于条款不存在。没有实际资料与召回证据前不引入向量数据库。

选择顺序：精确店铺 → 案例快照时间 → 适用范围 → 版本与冲突检查。店铺流程与型号手册可以互补并存；不能只因型号更具体便覆盖其他资料条件。明确版本重叠或已知矛盾交客服核查，不任取一份。第一版不声称能自动发现所有自然语言矛盾。

适用性筛选只用于项目内处理参考，不能覆盖程序固定资金权限和安全边界，也不构成真实品牌、合同或法规之间的效力顺序。

店铺、商品和时间取自已校验案例的服务端上下文，不能由模型输出覆盖。当前项目上传的店铺编号只是合成案例关联校验，不是生产环境商家身份认证；未来真实接入仍需账号及租户授权。

查询返回统一包，含status、reason_code、policy_mode、as_of、source、policies列表与冲突主题。每项规则包含实际编号、版本、条款编号、范围、有效期及来源。snapshot模式也包装成相同列表，不伪造库内规则编号。

| 情况 | 查询结果 | 对分析的影响 |
|---|---|---|
| 找到适用规则 | found | 提供真实条款与引用 |
| 未导入/无店铺规则 | not_found + no_policy | 资料缺失，保留其他可靠结果 |
| 尚未生效或已失效 | not_found + not_effective | 不把过期规则交给模型作现行依据 |
| 范围不符或缺范围信息 | not_found + scope_mismatch/scope_unknown | 不套用其他型号规则 |
| 同主题存在冲突 | conflict | 该主题交人工核对，其他无冲突主题可继续使用 |
| 模型请求其他店铺 | forbidden | 拒绝跨案例范围访问 |
| 存储查询失败 | error | 技术异常，不伪装成资料缺失 |

当部分主题存在冲突时，整体状态为conflict，policies仅包含可用的无冲突主题，并显式列出被排除的主题。工作流和结果校验必须分别处理，不能把整个包当成全部found。所有主题均无可用规则时policies为空。

## 6. 两种模式与可重复性

### 日常模式 registry

上传工单 → 校验并保存案例 → 创建运行 → 冻结该运行的规则选择结果 → Agent查询 → 根据事实与规则生成建议 → 保存结果和引用。

工单内policy原样作为输入快照保存，但不作为日常查询来源。JSON中的mode字段和客户要求不控制模式。缺少独立规则时明确报告，不读取工单内policy补位。

### 回放模式 snapshot

评估入口显式指定snapshot，查询只使用该工单内policy及其快照时间，不访问独立规则库。没有快照、快照过期或范围不符时按对应状态处理，不用当前规则补位。日常上传入口不开放给客户自行选择该模式。

既有快照兼容旧字段，不要求补写新的schema_version、scope或topic。它只属于该案例，按原有店铺关联和时间约束读取；applicability自由文本不升级为已核实的型号范围。只有采用新契约并校验发布的文件可以进入独立库，不自动把历史快照导入为通用规则。

查看已有运行始终读取已保存结果，不重新查询规则。对既有案例进行新的历史回放必须显式选择snapshot并创建新运行，不覆盖旧记录。若用户以后要求按当前库重新分析旧案例，属于registry模式的新运行，需明确时间基准，不能冒充历史重现。

每次registry运行开始时，在一次一致性读取中冻结候选文档版本、提取修订、正文、已知冲突、上下文、模式和时间。后续get_policy仅检索该运行快照，并记录查询词、检索器版本及实际返回的片段和顺序，避免中途发布导致前后不一致。snapshot模式保留原工单规则契约，不要求把旧工单或评估改成PDF。

## 7. 存储与模块职责

同一SQLite文件中新增独立表，复用现有运行数据库管理边界。运行产物仍在runtime中并被Git忽略。

| 表 | 内容 |
|---|---|
| policy_versions | 店铺/编号/版本、主题、范围、有效期、正文及来源JSON、正文哈希、发布时间 |
| policy_events | 导入发布、重复导入及旧版本有效期收口的受控审计记录 |
| run_policy_snapshots | run_id唯一、模式、时间、选择上下文、完整解析结果JSON及快照哈希 |

正文哈希验证条款和不可变来源内容；运行快照哈希覆盖完整选择结果与有效期。哈希用于一致性和追溯，不证明资料真实性。业务有效期变更单独审计。

推荐文件边界：`context/policy_schema.py`负责契约校验，`app/policy_repository.py`负责规则持久化，`workflows/policy_resolution.py`负责筛选与冻结，`tools/case_tools.py`只负责向Agent提供受限查询。维护命令放在对应维护入口，读工具不顺便发布规则。

规则仓储不能通过反复构造Storage触发现有重启中断逻辑；初始化只在应用启动或维护命令明确初始化时进行。已有cases、runs、events和历史result不回填、不改写。

## 8. 结果引用、缺口和安全

新结果增加policy_mode、policy_refs和policy_resolution。PDF引用列出实际文档编号、版本、文件哈希、提取修订、片段编号、原文、物理页码、来源和时间基准。旧快照保留原契约，不伪造PDF页码。原policy_version保留为程序生成的兼容展示摘要。

只有本轮实际调用get_policy后，才将返回的规则登记为已查询引用，标记usage=retrieved；冻结但尚未查询的规则只属于运行上下文。查到规则不等于已经采纳、裁决或执行。只有明确实现且通过事实校验的处理逻辑才能标记applied，第一版不声称已经自动执行自然语言条款。

普通客服页面仍只展示必要资料名称和版本摘要，详细引用放在现有证据/详情区域，不做界面美化。点击资料文件与任意路径访问仍属于TRACE-01，第一版不开放文件浏览接口。

GAP-01按实际状态分类：未调用get_policy为未查询，not_found为资料缺口，conflict为资料核对，error为技术异常。上述状态不要求客户提供店铺内部规则。

Agent仍只能建议；所有退款申请和金额决定交人工。安全提醒继续由程序生成，即使缺规则或规则正文包含越权指令也不能关闭。规则条款是引用资料，不作为system指令。

固定退款、安全和事实校验不依赖规则正文。第一版不执行自然语言规则引擎；如果结构化事实与规则使用方式无法核实，就保留事实并标记需客服核对，不由模型推断成退款资格获批。

## 9. 验证和验收

实现阶段至少覆盖：

1. 正常导入、重复导入幂等、同版本不同内容拒绝、整批事务回滚。
2. 店铺隔离、商品/品类精确匹配、缺少品类时只用通用规则。
3. 生效边界、失效边界、未来版本、明确替代与异常重叠。
4. registry不使用上传快照；snapshot不读取库；没有来源时均不自动回退。
5. 多主题选择、局部冲突、存储故障及对应信息缺口。
6. 运行中发布新版不改变当前运行；旧运行展示及原JSON不被改写。
7. 金额、退款权限、安全提醒与规则正文注入的回归。
8. 输出引用可定位真实版本，编造规则编号或条款不能进入已核实依据。

保留现有独立20条和开发20条输入及预期，运行时明确snapshot模式；不会为了规则库导入数据修改冻结的原案例。另建规则库专用用例和隔离数据库，明确发布内容、时间和预期匹配，评估报告记录模式、规则集版本与快照哈希。

规则查询行为或提示词发生变化后，提醒用户安排真实模型评估并人工复核。代码测试、预设判断回放、真实模型和人工业务验收分开报告，不以导入成功代替Agent正确使用规则。

## 10. 实施前评审要点

已确认来源模式，且用户明确原始资料应为PDF。本稿推荐PDF原件加登记信息、按页提取和SQLite检索，先支持可提取文字的PDF。需用专门用例验证解析完整性、中文召回、页码准确、无相关片段、PDF提示词注入与版本冻结。现无实际PDF，尚未验证解析质量；文中原条款校验及存储字段应在实施计划中映射为文档/片段契约，不采用手工重写PDF正文的路径。

文档评审完成后再拆分实施计划；当前仅设计，不安装依赖、初始化规则库、改变查询接口或修改业务代码。
