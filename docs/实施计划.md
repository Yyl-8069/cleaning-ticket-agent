# 清洁日用品工单 Agent 1.0 实施计划

> **实施要求：** 按任务逐项执行并勾选。实施前使用 superpowers:执行计划 技能。本计划采用当前会话直接实施，不调度子代理。

**目标：** 开发一个本机运行的网页应用：上传一份模拟工单案例 JSON，由 LangChain 单 Agent 调用只读工具分析，并保存可追踪的结果。

**架构：** FastAPI 提供上传、结果页和接口。明确的工作流负责校验、保存案例、创建运行记录、调用 Agent、检查输出和保存结果。SQLite 保存案例、运行及事件；结构化 JSON 日志与数据库事件共用 `run_id`，分别承担排障和页面追踪。

**技术栈：** Python、FastAPI、LangChain、DeepSeek API、SQLite、pytest、Python 标准日志库及按文件大小轮转。依赖版本在实施时核对兼容性并锁定，不在计划中填写未经验证的版本号。

**依据文档：** `D:\codex\project\清洁日用品工单Agent-1.0主要流程.md`

## 全局约束

- 产品代码放在 `D:\codex\project\cleaning-ticket-agent`，建立该项目自己的 Git 仓库。本计划目前位于 `D:\codex\project\docs\superpowers\plans`，创建项目后复制到项目 `docs/`。
- 每次导入一份 JSON，包含一张工单及其订单、商品、包裹、物流、规则和历史记录。基础样例：`D:\codex\skills\superpowers\ecommerce-agent-samples\case-001\initial-data.json`。
- 上传并校验成功后立即开始分析。只在本机运行，不接真实平台接口，不自动发送客户消息、创建物流核查、提交审批或退款。
- Agent 负责判断；工作流负责状态、时限、重试和持久化。工具只读，且每个工具只负责一种查询。
- API Key 从环境变量读取，不进入源码、日志或 Git；`.env.example` 仅放占位符。
- 项目根目录保留用户要求的九个目录：`agents/`、`tools/`、`skills/`、`workflows/`、`prompts/`、`context/`、`memory/`、`tests/`、`evals/`。暂未启用的能力只说明原因，不为填目录增加功能。
- `tests/` 检查代码，`evals/` 检查业务判断。模拟数据的结果不能写成真实店铺的成效。

## 重点复核的风险

1. JSON 损坏、工单与订单或客户编号不匹配时，必须在调用模型之前拒绝；任务 1 覆盖。
2. “查无订单”和“查询工具失败”必须区分；任务 2 覆盖。
3. 客户有条件地提出退款，不能被理解成退款已执行，也不能宣称已完成不存在的动作；任务 3 覆盖。
4. 同一案例上传两次，必须保留两次运行历史，原始案例不得被覆盖；任务 4 覆盖。
5. 模型或工具失败时，日志仍不能出现密钥或客户原文；任务 4 覆盖。

## 文件分工

| 项目内路径 | 职责 |
|---|---|
| `app/main.py`、`app/templates/index.html`、`app/templates/result.html` | 上传、运行状态和结果展示 |
| `context/case_schema.py` | 解析、校验导入案例 |
| `tools/case_tools.py` | 按案例范围执行单一职责查询 |
| `agents/ticket_agent.py` | LangChain 模型、工具绑定和分析输出 |
| `workflows/analyze_ticket.py` | 运行状态与失败分支 |
| `prompts/*.md` | 分模块、带版本的角色、任务、边界、示例和输出要求 |
| `app/storage.py` | SQLite 案例、运行、结果与事件 |
| `app/observability.py` | 结构化、脱敏、轮转日志 |
| `tests/`、`evals/` | 代码测试与业务案例评估 |
| `README.md`、`AGENTS.md`、`.env.example`、`.gitignore`、`pyproject.toml` | 运行说明、约定和可复现配置 |

`skills/` 与 `memory/` 在 1.0 只写简短说明。首条流程不需要自动写入长期客户记忆，也不需要专门开发项目技能。

### 任务 1：项目基础与案例契约

**文件：** 创建项目根目录、`context/case_schema.py`、`tests/test_case_schema.py`、`data/case-001.json`、基础配置和九个必需目录。

**接口：** `parse_case(raw: bytes) -> CaseBundle`。`CaseBundle` 提供类型明确的 `ticket`、`messages`、`order`、`order_items`、`product`、`shipments`、`policy`、`history`、`snapshot_at`。格式或关联错误抛出 `CaseValidationError`，包含字段路径和可安全展示的说明。

- [ ] 编写 `test_accepts_case_001`、`test_rejects_invalid_json`、`test_rejects_mismatched_order_customer`、`test_rejects_oversize_upload`，确认实现前按预期失败。
- [ ] 实现 JSON、必要字段、跨对象编号、时间和金额校验。上传大小起步上限建议为 1 MiB，并写入说明；不接受 JSON 指定任意本地文件路径。
- [ ] 运行 `pytest tests/test_case_schema.py -q`；初始化项目 Git，检查 `.gitignore` 后提交通过测试的案例契约。

### 任务 2：SQLite 存储与只读业务工具

**文件：** `app/storage.py`、`tools/case_tools.py`、`tests/test_storage.py`、`tests/test_case_tools.py`。

**接口：** `save_case(bundle: CaseBundle) -> str`、`create_run(case_id: str) -> str`、`get_run(run_id: str) -> RunRecord`。`get_ticket`、`get_order`、`get_product`、`get_shipments`、`get_history`、`get_policy` 接收受限的案例仓储与编号，返回“找到 / 未找到 / 出错”及来源、观察时间。模型不能自行指定任意店铺或客户范围。

- [ ] 编写空库初始化、案例读回、查无订单与查询错误、跨案例拒绝查询、同一案例多次运行的测试，确认实现前失败。
- [ ] 实现 SQLite 表与单一职责查询工具。上传案例中的规则版本作为模拟快照保存，通过工具读取；Agent 初始输入不直接包含整个案例答案。
- [ ] 运行 `pytest tests/test_storage.py tests/test_case_tools.py -q` 并提交。

### 任务 3：LangChain 分析与业务评估

**文件：** `agents/ticket_agent.py`、`prompts/system.md`、`prompts/task.md`、`prompts/constraints.md`、`prompts/examples.md`、`prompts/output-schema.json`、`evals/cases/`、`evals/run_evals.py`、`tests/test_ticket_agent.py`。

**接口：** `analyze_ticket(case_id: str, run_id: str, toolset: CaseTools) -> AnalysisResult`。结果包含 `intent`、带来源的 `verified_facts`、`missing_information`、`recommendation`、`reply_draft`、`policy_version`、`status`，并由程序校验。工具调用次数和总时长必须有限；起步值在本机试跑后写入 README，不声称为最佳参数。

- [ ] 用模拟模型编写结构化输出、无依据事实、规则缺失、工具调用超限及模型超时测试，确认实现前失败。
- [ ] 实现 LangChain 单 Agent 和分模块提示词。实施时核对 DeepSeek 当前工具调用文档，选择兼容的模型与接口模式；不保存模型隐式思维链。
- [ ] 建立小型固定评估集：CASE-001，以及缺订单、过期规则、工具失败、提示词注入变体。CASE-001 必须询问客户是否现在申请退款，不能宣称已经建单或退款完成。
- [ ] 运行 `pytest tests/test_ticket_agent.py -q` 和使用模拟模型的固定评估；配置本地密钥后做一次 DeepSeek 真实调用冒烟检查，记录模型版本、token、耗时与可获取的费用。提交代码、提示词和脱敏案例，不提交密钥或原始模型轨迹。

### 任务 4：工作流、日志与可恢复的运行记录

**文件：** `workflows/analyze_ticket.py`、`app/observability.py`、`tests/test_workflow.py`、`tests/test_observability.py`。

## 完成标准

五个固定案例的输出结构均合法，不得编造“已完成”的业务动作。CASE-001 必须保留有条件退款意图，并引用订单、物流和规则来源。全部代码测试通过，每次运行都有可追溯的终止状态。记录真实观察到的业务表现、成本和耗时，不虚构目标已达成，也不宣称已有真实商家使用。
