# 清洁日用品工单 Agent 1.0

面向清洁类日用品售后的工单分析项目：上传店铺售后工单 JSON，FastAPI 校验并保存案例，LangChain 单 Agent 按需调用只读工具查询，生成事实依据、处理建议和回复草稿。SQLite 保存每次分析，网页刷新后仍可查看。不会接入真实平台、发送回复、建物流工单或退款。

## 版本进程

1.0 已作为可运行雏形归档；1.1 开发已完成运行中的网页自动更新与正式来源名称展示。候选、实际完成状态和历史问题统一记录在 [开发进程](docs/开发进程.md)。能力缺口分类、客服界面简化和可点击来源路径仍在待办中。仓库使用合成数据样例，当前没有连接真实店铺接口；公开发布准备单独维护。

## 环境与运行

建议 Python 3.12，PowerShell：

```powershell
cd D:\codex\project\cleaning-ticket-agent
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
$env:DEEPSEEK_API_KEY = "你的密钥"
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打开 `http://127.0.0.1:8000`，每次上传 `data/case-001.json` 至 `data/case-006.json` 中的一份。新增样例依次覆盖未发货催促、明确申请退款、清洁剂漏液、双瓶装少件和退款到账咨询；均为样例数据，需核对事实与规则后才能用于真实业务。停止服务按 Ctrl+C。密钥也可保存在未提交的 `.env` 中，但当前程序不会自动加载 `.env`；启动前需写入进程环境变量。未设置密钥时上传仍会保存案例，分析状态会显示 `failed`，不会生成虚假结果。

分析中页面每2秒自动更新，完成后自动显示结果；分析完成、失败或中断后停止更新。更新只读取现有记录，不会重复导入或调用模型。

事实来源按资料类别显示业务名称，并注明取自本次上传工单；原始来源字段保留。旧来源引用缺失或无法识别时显示“上传资料”。重启服务后刷新旧结果页即可应用新显示，无需重新分析。

一次仅支持一份 UTF-8 JSON、单工单，最大 1 MiB；仅接受 `metadata.synthetic=true` 的样例案例。重复上传生成独立案例和运行记录，不覆盖已有数据。数据库和 JSONL 日志位于 `runtime/`，均不进入 Git。日志按 2 MB 轮转，保留 5 个备份文件；终端和文件记录事件类型、工具状态、每次模型调用耗时与 token 用量、运行总耗时，不存原始客户文本、密钥或模型推理过程。Uvicorn 启动时在终端显示服务端口。

## 验证

```powershell
python -m pytest tests -q
python -m evals.run_evals
python -m evals.run_evals --offline-replay
```

第二条只校验 11 个样例输入（6 个原始工单 + 5 个历史边界案例）。第三条用**预设业务判断**回放真实工具、校验器、工作流和 SQLite，验证流程，不能证明模型识别正确。

在已经配置 `DEEPSEEK_API_KEY` 的终端执行：

```powershell
python -m evals.run_evals --live
```

这会调用 DeepSeek 并产生模型费用。评分核对诉求、退款意向、结构化事实、必需动作、禁止动作与工具选择；模型决策需要程序纠正时也会计入失败。语义质量仍需逐条人工复核。原始样例工单没有被改写以迎合评分。

结果分别保存在 `runtime/evals-offline.db`、`runtime/evals-live.db` 及对应 `evals-<mode>-summary.json`、JSONL 日志中，和网页运行数据库分开。费用缺少计价依据时标记 `unknown`。模型调用后校验失败的用量目前保留在调用日志中，评估摘要尚未自动汇总，不能把空值当零费用。

2026-10-30 修复验证记录：65 条代码测试通过，11 个输入校验和11条预设判断流程回放通过。此前修复阶段没有可用密钥，未进行新的模型回放。随后只读核对本地历史，已有6份带模型用量的新版结果，覆盖5个案例；部分结果仍存在分类或动作问题，不能据此认定完整业务验收通过，详见开发进程。默认模型为 `deepseek-flash`，可用 `DEEPSEEK_MODEL` 覆盖。

固定集包含缺订单、缺规则、缺物流、提示词注入，以及六个清洁用品售后工单。没有真实商家数据；过期规则和运行中工具异常的业务评估仍待扩充，代码测试已覆盖对应基础行为。

## 结构与限制

`app/` 是 HTTP、SQLite 和日志；`context/` 校验输入；`tools/` 只读查询；`agents/` 负责模型判断；`workflows/` 控制状态；`prompts/` 版本化提示词；`tests/` 是程序测试；`evals/` 是业务案例。`skills/` 暂不引入项目内技能，`memory/` 关闭跨工单长期记忆。

1.0 使用 FastAPI 后台任务。服务器真正启动时将未完成运行标记为 `interrupted`，不会自动重试；仅导入应用模块不会打开默认数据库或改写运行状态。页面无账号认证，只适合本机 `127.0.0.1`。

本轮使用提示词 2.0 和结果结构 v2：LangChain Agent 负责理解诉求、查询工具、选择退款意向及下一步。`context/result_grounding.py` 使用实际查询的订单、物流和退款流水生成事实及安全回复，不把模型自由文本当作已证实事实。`not_found` 是有效空查询，只表示当前快照没有对应数据。历史退款金额、流水、订单编号及时间一致才允许说明退款成功，仍不能证明支付渠道到账。

业务待办与技术状态分开：补照片、查规则、交客服审核都可以是“分析完成”。仅证据冲突显示“需核对的具体事项”，不再因出现“已退款”字样把整单变成人工复核。模型超时、非法输出和越权来源仍可失败。网页显示总耗时 ms；旧运行保持原样，需要重新上传才能生成新版本结果。

模型的动作受到意向及余额约束：有条件退款不作为立即退款授权，已全额退款不再建议重复退款。程序对模型动作的纠正写入 `decision_adjusted` 日志和结果 `decision_adjustments`，不隐藏模型决策错误。样例规则不是平台官方政策，尚未实现自然语言规则的通用自动裁决。

首版只覆盖七类诉求，回复采用固定安全语句组合，表达灵活性有限；复杂、多意图诉求仍需扩展枚举、话术和评估。商品图片只记录是否存在，未做图像识别；目录规格不等于实物装箱证据。不会真正执行退款、审批、发消息或结单。

更新代码后，在原来设置了密钥的终端按 Ctrl+C 停止服务，再执行原启动命令；仅刷新旧结果页面不会重新分析。请勿把密钥或完整终端历史发到聊天中。

## Git 上传准备

初学者按 [Git 入门](docs/Git入门.md) 逐步操作。

项目已是独立 Git 仓库。先执行 `git status`、`git diff --check`、上面的测试与评估，确认 `.env`、`runtime/` 不在暂存区，再 `git add .`、`git diff --cached --stat`、`git commit -m "实现工单 Agent 1.0"`。上传需要你自己的远端仓库地址；取得地址后执行 `git remote add origin <仓库地址>` 和 `git push -u origin develop`。如果远端已有提交，需要先核对分支和历史，不能盲目强推。
